--- SECTION 2: IP-in-IP ---

A16.
RFC = RFC 2003 (IP Encapsulation within IP)
Protocol Number = 4 (decimal) = 0x04 (hex)
IP header-ல் Protocol=4 இருந்தா
"Next header = another IP packet" என்று router புரியும்.

A17.

= Multiple vendor implementations affected
= Devices decapsulate IP-in-IP WITHOUT validation

  arbitrary traffic through vulnerable device
= Access control bypass, spoofing possible.
Affected: Cisco, Linux, many others.

A18.
Vulnerable device skips:
1. Is outer source IP an authorized tunnel endpoint?
2. Is a tunnel configured with this source?
3. Is inner source IP valid/authorized?
4. Any cryptographic verification.

→ forwards inner packet without ANY check!

A19.

A20.
GRE structure:
[Outer IP][GRE Header 4+ bytes][Inner IP][Payload]
IP-in-IP structure:
[Outer IP][Inner IP][Payload]
Key difference:
IP-in-IP = NO intermediate header!
Protocol=4 in outer IP tells receiver "inner = IP".
= Simpler, smaller (4+ bytes less).
= Same attack capability.

A21.

Step 2: Protocol=4 detected.

Step 5: Device forwards inner packet to multicast group.
Step 6: All multicast subscribers receive.
= Target devices = zero config needed.

--- SECTION 3: EtherIP ---

A31.
RFC = RFC 3378 (EtherIP: Tunneling Ethernet Frames)
IP Protocol Number = 97 (0x61)
Purpose: Carry Ethernet frames inside IP packets.
= L2 over L3 tunneling.
= Connect two Ethernet LANs over IP network.

A32.
EtherIP header size = 2 bytes ONLY!
Fields:
Bits 0-3:  Version = 3 (always value 3!)
Bits 4-15: Reserved = 0 (always zero!)
Total: 16 bits = 2 bytes.
= No auth field, no session ID, no key!
= Simplest possible tunnel header.

A33.
GRE carries: IP packets (L3 payload)
IP-in-IP carries: IP packets (L3 payload)
EtherIP carries: Full Ethernet FRAMES (L2 payload!)
Difference: EtherIP inner = complete ETH frame
including MAC addresses, EtherType, etc.
= L2 access! ARP, STP, DHCP all possible.
GRE/IP-in-IP = IP level only.

A34.
EtherIP inner payload = Layer 2 (Data Link Layer)
Full Ethernet frame = MAC src, MAC dst, EtherType.
Then inside ETH frame: IP (L3), TCP (L4), Data (L7).
Stack: L3 outer → EtherIP (2B) → L2 → L3 → L4 → L7.

A35.
CVE-2021-0328 = EtherIP unauthenticated decapsulation.
Affected: Cisco IOS, FreeBSD, OpenBSD, NetBSD, Linux.
Vulnerable behavior:
Receives Proto=97 → immediately decapsulates
→ forwards inner ETH frame to bridge
→ NO tunnel config check!
= Anyone can inject Ethernet frames!

A36.
EtherIP bypasses RPF because:
1. Inner ETH frame → bridge (L2 processing).
2. Bridge operates at L2.
3. RPF = L3 concept (checks routing table).
4. L2 bridge doesn't perform RPF checks!
5. Frame delivered to interface as "local frame".
6. THEN IP layer processes it from that interface.
7. RPF check: "came from Gi0/1?" YES (bridge delivered there).
= Even strict RPF passes!

A37.
L2 attacks possible via EtherIP:

A38.
EtherIP Version field = 3 (binary: 0011)
Always must be 3.
Occupies bits 0-3 of the 2-byte header.
Remaining 12 bits = Reserved = 0.
No other version values are defined.

--- SECTION 4: NAT + ENCAPSULATION ---

A46.
IPSec AH breaks NAT technical reason:
1. AH = Authentication Header.
2. AH computes ICV (Integrity Check Value) over:
   IP source address + IP dest address + payload.
3. NAT changes source IP address.
4. Changed IP → ICV verification FAILS at receiver.
5. Receiver: "Packet modified! Reject!"
6. NAT-T cannot help: AH covers outer IP headers.
= Fundamentally incompatible. Use ESP instead.

A47.
NAT-T = NAT Traversal for IPSec.
Port = UDP 4500.
Mechanism:
ESP packet (Proto=50, no port) → NAT drops.
NAT-T wraps ESP inside UDP 4500:
[IP][UDP 4500][Non-ESP Marker=0x00000000][ESP][Payload]
NAT tracks UDP 4500 port → works through NAT.
Negotiated via IKE: detects NAT in path, switches to 4500.

A48.
PPTP GRE Call ID for NAT multiple clients:
Normal GRE = no port → NAT can't track multiple clients.
Enhanced GRE (PPTP): Key field = Call ID (16-bit).
Each PPTP client gets unique Call ID.
NAT table: {private IP, Call ID} → {public IP, mapped CID}.
Client 1: 192.168.1.10, CID=0x1234
Client 2: 192.168.1.11, CID=0x1235
NAT distinguishes by CID → multiple clients work!

A49.
Protocols with NO authentication by default:
1. GRE (raw) — no auth, no encryption
2. IP-in-IP — no auth, no encryption
3. VXLAN — no auth, VNI = just an ID
4. MPLS — no auth (RFC 3031 confirms)
5. 6in4 — only src IP check (weak)
6. EtherIP — no auth, no session ID
7. L2TP standalone — no data channel encryption

A50.
ICV = Integrity Check Value in IPSec AH.
Computation: HMAC(key, IP_src + IP_dst + AH_hdr + payload).
NAT breaks it:
Step 1: AH computed with src IP = 192.168.1.10.
Step 2: NAT changes src IP to 1.2.3.4.
Step 3: Receiver computes ICV with 1.2.3.4.
Step 4: ICV mismatch! (was computed with 192.168.1.10)
Step 5: Packet REJECTED.
= NAT + AH = always broken.

Applied via: service-policy global_policy global

A52.
Raw GRE + Dynamic NAT failure reason:
GRE = IP protocol 47, NO port number.
NAT needs port number to track sessions.
Multiple clients → same proto → cannot distinguish.
Static 1:1 NAT: entire public IP maps to one private IP.
No port needed → one GRE session works.
Dynamic NAT/PAT: needs port → GRE has none → drops!

A53.
MS-CHAPv2 weaknesses in PPTP:
1. Based on MD4 hash (broken algorithm).
2. NTResponse = DES(MD4(password), challenge).
3. DES = 56-bit key = crackable.
4. MD4 = vulnerable to rainbow tables.
5. Tools: chapcrack, asleap, cloudcracker.
6. Offline attack: capture handshake → crack.
7. Time to crack: hours to days with GPU.

A54.
PPTP encryption cipher = RC4-40 bit.
RC4-40 = export-grade cipher (legacy US export law).
Weaknesses:
1. 40-bit key = only 2^40 combinations.
2. RC4 = stream cipher with known biases.
3. Crackable in hours with modern hardware.
4. "40-bit" = deliberately weakened!
5. MS-MPPE (encryption) = RC4-128 in newer versions
   but still uses weak MS-CHAPv2 for auth.

A55.
Strong authentication VPN protocols (3 examples):

A56.

Value = 0x00000000 (4 zero bytes).
Purpose: Distinguish IKE traffic from ESP traffic

IKE packet: first 4 bytes = non-zero (ISAKMP header).

--- SECTION 5: RPF + MARTIAN CHECKS ---

A61.
RPF = Reverse Path Forwarding.
Purpose: Anti-spoofing mechanism.
Logic: "From which interface should this source IP arrive?"
If packet arrives from wrong interface → DROP!
Checks routing table: "Best route to src IP via which interface?"
If actual arrival interface ≠ best route interface → FAIL (strict).
If route just exists (any interface) → PASS (loose).

A62.
Strict RPF:
Packet must arrive on the EXACT interface
that the routing table says is best for that src IP.
= Strictest check. Any deviation → DROP.

Loose RPF:
Route to src IP must EXIST in routing table.
Doesn't check which interface it arrives on.
= More permissive. Only verifies route exists.

No RPF:
No check at all.
= Any source IP passes.

A63.
Unused IP (e.g., 150.134.23.99) bypasses loose RPF:
1. 150.134.23.99 in 150.134.23.0/24 subnet.
2. 150.134.23.0/24 = connected route on Gi0/1.
3. Route EXISTS in routing table ✅
4. Loose RPF: "Route exists? YES → PASS!"
5. Doesn't check if correct interface.
= RPF bypass success with unused subnet IP!

A64.
Linux sysctl parameter for RPF:
net.ipv4.conf.all.rp_filter
Values:
0 = No RPF check
1 = Strict RPF (best route interface must match)
2 = Loose RPF (route must exist anywhere)
Default on most distros = 2 (loose).
Set per interface: net.ipv4.conf.eth0.rp_filter

A65.
If inner src = router's own GRE interface IP (203.0.113.1):
RPF check: "203.0.113.1 should arrive from... Gi0/0 (local!)"
CEF check: "203.0.113.1 = MY OWN LOCAL ADDRESS!"
Result: MARTIAN! DROP immediately!
Reason: Own IP appearing as transit source = impossible/spoof.
= 100% always dropped. No exception.

A66.

1. Router's own interface IPs (locally originated)
   e.g., 203.0.113.1 if that's router's Gi0/0.

   (127.0.0.1 = local only, never transit)

"Cannot neighbor with myself!" → DROP.

A68.

After bridge delivers to Gi0/1 as local frame:

A70.
CEF = Cisco Express Forwarding.
= Hardware-accelerated packet forwarding in Cisco routers.
Martian check relation:

FIB includes local address table.
When decapsulated inner src checked:
CEF looks up src IP in local address table.
Found? = Martian → DROP.
Not found? = Continue processing.
= CEF is the enforcement mechanism for martian checks.

A71.

Router's addresses: 203.0.113.1, 150.134.23.1, 198.51.100.1.
Unused IP = 150.134.23.99.
150.134.23.99 ≠ any of router's IPs.

--- SECTION 9: VXLAN + NVGRE + GENEVE ---

A121.
VXLAN details:
UDP port = 4789 (IANA assigned)
VNI (VXLAN Network ID) = 24 bits
24 bits = 2^24 = 16,777,216 possible segments!
(vs VLAN = 12 bits = 4094 segments)
VNI in VXLAN header = last 3 bytes of 8-byte header.
Flag byte: I-bit must be set (I=1) for VNI to be valid.

A122.
VXLAN BUM (Broadcast, Unknown unicast, Multicast) forwarding:
1. Admin assigns multicast group per VNI.
   e.g., VNI 100 → multicast group 239.1.1.1.
2. All VTEPs for VNI 100 join 239.1.1.1.
3. BUM traffic sent to 239.1.1.1 (outer IP dst).
4. All VTEPs in group receive it.
5. Each VTEP decapsulates → delivers to local VMs.
= Flood to all VTEPs using IP multicast!

A123.
NVGRE = Network Virtualization GRE (Microsoft).
RFC = Microsoft proprietary (Windows Server 2012+).
Standard GRE Key field = optional tunnel ID.
NVGRE: Key field = VSID (Virtual Subnet ID, 24 bits)
             + FlowID (8 bits for load balancing).
NVGRE EtherType = 0x6558 (Ethernet in GRE).
Standard GRE = any payload.
NVGRE = Ethernet frames inside GRE + VSID for segmentation.
Used in: Hyper-V, Azure (historically).

A124.
VSID = Virtual Subnet ID in NVGRE.
Size = 24 bits (upper 24 bits of GRE Key field).
Range = 0 to 16,777,215.
Purpose: Identify virtual network segment.
Similar to VXLAN VNI (also 24 bits).
Lower 8 bits of GRE Key = FlowID (entropy for ECMP).
VSID 100 = separate virtual network = isolated broadcast domain.

A125.
GENEVE = Generic Network Virtualization Encapsulation.
UDP port = 6081.
RFC = RFC 8926 (2020).
Designed to replace VXLAN + NVGRE + STT.
Key feature: Extensible TLV options in header.
Protocol type field: what inner payload is
(e.g., 0x6558 = Ethernet, 0x0800 = IPv4).
VNI field = 24 bits (same as VXLAN).

A126.
GENEVE vs VXLAN extensibility:
VXLAN header = fixed 8 bytes. No options.
GENEVE header = variable length with TLV options!
TLV = Type, Length, Value.
Options can carry: metadata, security context,
   encryption keys, tenant info, etc.
Option Len field in GENEVE = specifies header size.
= GENEVE more flexible for SDN/NFV.
VXLAN-GPE = attempt to extend VXLAN (less flexible).

A127.
For targeted VXLAN VNI segment attack:
Attacker needs to know:
1. VTEP IP address (outer dst).
2. VNI number of target segment.
3. Target VM's MAC address (for unicast) or broadcast.
VNI scanning: try VNI 0-16777215, see responses.
Tools: vxlan-scan, custom scapy scripts.
No auth = brute force VNI trivially easy.

A128.
VNI scanning:
Attack: Send VXLAN packets with VNI 1, 2, 3... 16777215.
Send inner ARP request inside each.
If response received = VNI exists! Active segment!
Security risk:
1. Enumerate all active virtual networks.
2. Map tenant segments.
3. Target specific tenant's VMs.
4. Inject into discovered segments.
No authentication = VNI is just a number, not a secret.

A129.
VXLAN built-in authentication: NO!
VNI = identifier, not authenticator.
No cryptographic protection in RFC 7348.
Security implications:
1. Anyone can inject VXLAN packets to VTEP.
2. VNI can be scanned/guessed.
3. Inner frames not encrypted.
4. Man-in-the-middle possible.
Mitigation: VXLAN over IPSec, or VXLAN-GPE with security.
Production: Often deployed without auth = RISK!

A130.
NVGRE EtherType for Ethernet payload:
Protocol field in GRE = 0x6558
0x6558 = Transparent Ethernet Bridging.
= "Inner payload is a raw Ethernet frame!"
Same value used in standard GRE for L2 carry.
NVGRE uses this to carry VM-to-VM Ethernet frames.
Followed by: full Ethernet frame (dst MAC, src MAC, type).

A131.
VXLAN BUM flooding multicast range:
Typically admin-scoped multicast: 239.0.0.0/8.
239.0.0.0/8 = Organization-local scope (RFC 2365).
Example ranges:
239.1.1.0/24 = VNI-to-multicast mapping
VNI 100 → 239.1.1.100
VNI 200 → 239.1.1.200
(mapping is configurable, not standard).
224.0.0.0/4 = all multicast = technically usable.

A132.
NVGRE vs VXLAN multiple virtual networks:
Both use 24-bit segment identifier.
NVGRE: VSID (Virtual Subnet ID) in GRE Key.
VXLAN: VNI (VXLAN Network ID) in VXLAN header.
NVGRE transport: GRE (IP proto 47).
VXLAN transport: UDP 4789 (NAT-friendly!).
NVGRE = harder with NAT (GRE, no port).
VXLAN = NAT-friendly (UDP has port).
VXLAN = won industry adoption over NVGRE.

A133.
LISP = Locator/ID Separation Protocol.
RFC = RFC 6830.
Data plane UDP port = 4341.
Control plane = Map-Server/Map-Resolver.
Purpose: Separate endpoint ID from routing locator.
Used in: Cisco SD-Access, SD-WAN.
Attack surface: Map-Register, Map-Notify spoofing.
Instance ID = LISP equivalent of VNI (32 bits).

A134.
GENEVE TLV options attack surface:
Options are variable-length, extensible.
Each TLV: Type (2 bytes) + Length (1 byte) + Value.
Attack possibilities:
1. Inject malformed TLVs → crash parsing code.
2. Spoof metadata TLVs → bypass security policies.
3. Inject security context TLVs → policy bypass.
4. Overflow option parsing → buffer overflow potential.
5. Type confusion attacks via unknown TLV types.
VXLAN has no options = less attack surface there.

A135.
VXLAN vs NVGRE transport protocol:
VXLAN = UDP (User Datagram Protocol) port 4789.
NVGRE = GRE (IP Protocol 47), no port.
Impact:
VXLAN = NAT traversal easy (UDP has port).
NVGRE = NAT problematic (GRE = no port).
VXLAN = Load balancing easy (UDP src port for ECMP).
NVGRE = FlowID field for load balancing.
VXLAN = Won: cloud providers, open source adopted VXLAN.
NVGRE = Mostly Microsoft Azure (legacy).

--- SECTION 10: IP OPTIONS + SOURCE ROUTING ---

A136.
Three IP option types for routing:
1. Record Route: Type=7 (0x07)
   = Each router records its IP. Path discovery.
2. Strict Source Route (SSR): Type=137 (0x89)
   = Packet MUST follow exact specified path.
3. Loose Source Route (LSR): Type=131 (0x83)
   = Packet MUST visit specified IPs (any path between).

A137.
SSR vs LSR:
SSR (Strict):
Packet must follow EXACT sequence of specified IPs.
ANY deviation from path = packet DROPPED.
Very rigid. Modern networks mostly block.

LSR (Loose):
Packet must VISIT specified waypoints in order.
Between waypoints: any path allowed!
More flexible. Better for firewall bypass.
Both: Destination IP in main header shifts as packet traverses.

A138.
Record Route IP option (Type=7):
Each router along path WRITES its outgoing interface IP
into the Record Route option field.
Attacker sends packet with empty RR slots.
Packet returns with ALL router IPs filled in!
Reveals: Internal router IPs, private RFC1918 addresses,
network topology, hop count, intermediate devices.
= Passive topology discovery!

A139.
IP option type byte structure (8 bits):
Bit 7: Copied flag (1=copy to fragments, 0=don't)
Bits 6-5: Option class (00=control, 10=debug)
Bits 4-0: Option number (5-bit number)
Examples:
RR=0|00|00111 = 00000111 = 7
SSR=1|00|01001 = 10001001 = 137
LSR=1|00|00011 = 10000011 = 131
Copied=1 for SSR/LSR = copied to fragments!

A140.
LSR + SNMP for topology discovery:
