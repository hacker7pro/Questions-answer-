SECTION F: VENDOR DEFAULT BEHAVIOR
────────────────────────────────────────────────────────────────

Q51. Cisco IOS default-ஆக IP options handle பண்ணுவது எப்படி?
A51. Cisco IOS default = ALLOW (pass-through).
     IP options உள்ள packets default-ஆக forward ஆகும்.
     No automatic blocking.
     Router LSR/SSR options follow பண்ணும் — traffic redirect possible.
     Manual block தேவை:
       ip options drop        (global command)
     Verify current behavior:
       show running-config | include ip options
     Note: IOS 12.4+, 15.x = ip options drop available.
     Older IOS: ACL மூலம் மட்டுமே block possible.

────────────────────────────────────────────────────────────────

Q52. Cisco IOS default-ஆக GRE, IP-in-IP, EtherIP handle பண்ணுவது எப்படி?
A52. Cisco IOS defaults (Router mode):
     GRE   (Proto 47): ALLOW — pass-through
     IP-in-IP (Proto 4): ALLOW — pass-through
     EtherIP  (Proto 97): ALLOW — pass-through
     6in4  (Proto 41): ALLOW — pass-through
     Reason: Cisco IOS router = forward packets, not inspect.
     "Routing function first, security second" philosophy.
     Pen test implication: Fresh IOS router = all encap protocols pass.
     Hardening required: Explicit ACL deny for each protocol.

────────────────────────────────────────────────────────────────

Q53. Cisco ASA-ல் IP options default behavior என்ன?
A53. Cisco ASA default = DENY IP options (secure by default).
     ASA automatically drops packets with:
     - LSR (Option 131)
     - SSR (Option 137)
     - Record Route (Option 7)
     - Timestamp (Option 68)
     - Router Alert (Option 148)
     ASA drop reason: "ip-options"
     Verify: show asp drop frame ip-option-drop
     Override (allow specific): ip options {option-name} allow
     ASA philosophy: "Security first" — deny unknown/suspicious.

Q54. Cisco ASA-ல் GRE மற்றும் 6in4 default behavior என்ன?
A54. Cisco ASA defaults:
     GRE (Proto 47):  ALLOW — stateful inspection
     IP-in-IP (Proto 4): DENY — not typical traffic
     EtherIP (Proto 97): DENY — unknown/unusual
     6in4 (Proto 41): ALLOW (if IPv6 inspection enabled)
     IPSec ESP (50): ALLOW (IPSec pass-through by default)
     Note: GRE allow ஆனால் inspection shallow.
     "inspect gre" command deeper inspection enable பண்ணும்.
     ASA 9.x+: GRE tunnel endpoint tracking available.

Q55. FortiGate FortiOS default encapsulation behavior என்ன?
A55. FortiGate defaults:
     IP Options: PARTIAL — depends on IPS profile
     GRE   (47): ALLOW — implicit permit (no explicit block)
     IP-in-IP (4): ALLOW — implicit permit
     EtherIP (97): ALLOW — no built-in block
     6in4  (41): ALLOW — implicit permit
     IPSec (50): ALLOW — VPN use case
     FortiGate philosophy: "Application-aware, but permissive base"
     Important: FortiGate policy default = deny all UNLESS explicit allow.
     But protocol-level L3 pass-through can occur before policy match.
     Hardening: Explicit deny service objects for proto 4/47/97.

Q56. Juniper SRX default zone-based behavior encapsulation-க்கு என்ன?
A56. Juniper SRX defaults:
     IP Options: DENY — implicit via zone policy
     GRE   (47): PARTIAL — inter-zone permit required
     IP-in-IP (4): DENY — not default permitted
     EtherIP (97): DENY — unknown proto, inter-zone blocked
     6in4  (41): DENY — IPv6 explicit config needed
     IPSec (50): PARTIAL — IKE negotiation required
     SRX philosophy: "Zone-based — no implicit inter-zone permit"
     Default: trust→untrust = permit outbound
     untrust→trust = DENY all unless explicit policy.
     Most secure default among major vendors.

Q57. Linux kernel default encapsulation protocol behavior என்ன?
A57. Linux kernel defaults:
     IP Options: ALLOW — kernel passes through
     GRE   (47): ALLOW (if ip_gre module loaded)
     IP-in-IP (4): ALLOW (if ipip module loaded)
     EtherIP (97): ALLOW — raw socket receive possible
     6in4  (41): ALLOW (if sit module loaded)
     IPSec (50): PARTIAL (strongSwan/libreswan needed)
     Linux philosophy: "Permissive kernel, security via iptables"
     Default iptables = ACCEPT all (no rules loaded at boot).
     Hardening: Load iptables/nftables rules at startup.
     Check loaded modules: lsmod | grep -E "ipip|gre|sit"

Q60. pfSense/OPNsense default encapsulation behavior என்ன?
A60. pfSense/OPNsense (FreeBSD pf) defaults:
     IP Options: DENY — pf "scrub" rule strips options
     GRE   (47): ALLOW — pass rule needed but proto not blocked
     IP-in-IP (4): ALLOW — pf pass-through
     EtherIP (97): ALLOW — unknown proto pass-through
     6in4  (41): ALLOW — IPv6 transition support
     IPSec (50): ALLOW — auto-generated IPSec rules
     pf scrub command (pf.conf):
       scrub in all no-df random-id reassemble tcp
     This strips IP options automatically.
     But other encap protocols not blocked by default.

Q61. Vendor comparison-ல் "most secure by default" யார்?

     1. Juniper SRX — Zone deny-by-default, explicit permit needed

Q65. "Default deny, selective allow" strategy என்றால் என்ன?
A65. Strategy:
     Default: DENY all encapsulation protocols (4, 41, 47, 97, 50)
     Exception: PERMIT only from/to trusted IP list
     Implementation order (ACL):
       Line 1: permit proto X from trusted_host_A    ← first
       Line 2: permit proto X to   trusted_host_A
       Line 3: deny   proto X any any log             ← catch all
       Line 4: permit ip any any                      ← normal traffic
     Critical: Cisco ACL = top-down processing.
     Trusted entries must be BEFORE blanket deny.

Q69. nftables set-based approach trusted IPs manage பண்ண எப்படி?
A69. nftables sets (dynamic update possible):
     table inet filter {
       set TRUSTED_GRE {
         type ipv4_addr
         elements = { 203.0.113.10, 203.0.113.20 }
       }
       set TRUSTED_ETHERIP {
         type ipv4_addr
         elements = { 192.168.10.5 }
       }
       chain forward {
         type filter hook forward priority 0; policy drop;
         ip protocol 97 ip saddr @TRUSTED_ETHERIP accept
         ip protocol 97 ip daddr @TRUSTED_ETHERIP accept
         ip protocol 97 log prefix "ETHERIP-BLOCKED: " drop
         ip protocol 47 ip saddr @TRUSTED_GRE accept
         ip protocol 47 ip daddr @TRUSTED_GRE accept
         ip protocol 47 log prefix "GRE-BLOCKED: " drop
         ct state established,related accept
         ip protocol tcp accept
         ip protocol udp accept
       }
     }

Q74. ACL order தப்பினால் என்ன ஆகும்? Example கொடு.
A74. Wrong order example:
     WRONG:
       deny 47 any any         ← இது first match
       permit 47 host A any    ← never reached!
     Result: Trusted host A-ம் block ஆகும்.

     CORRECT:
       permit 47 host A any    ← trusted first
       deny 47 any any         ← then block rest
     Result: Host A allow, others block.

     Cisco ACL rule: First match wins. Top-down processing.
     Always: trusted entries → TOP
             blanket deny   → BOTTOM

Q78. Rate limiting encapsulation protocols DoS prevent பண்ண Cisco IOS config?

Q79. Snort 3.0-ல் GRE inner payload HTTP detect பண்ண rule எழுது?
A79. Snort 3.0 rule:
     alert ip any any -> any any (
       msg:"HTTP GET inside GRE tunnel";
       ip_proto:47;
       raw_data;
       content:"|00 00 08 00|";  offset:0; depth:4; (GRE header)
       content:"GET "; offset:24; depth:4;
       sid:3000001; rev:1;
       metadata:policy security-ips alert;
     )
     Alternative: Use preprocessors
       preprocessor gre: both
     Then normal HTTP rules apply to inner payload.

Q80. Linux kernel-ல் GRE module unload செய்தால் protocol 47 traffic block ஆகுமா?
A80. Module unload analysis:
     GRE module: ip_gre
     Unload: modprobe -r ip_gre
     Effect:
     - New GRE tunnels create ஆகாது
     - Existing tunnels down ஆகும்
     - BUT: protocol 47 packets still pass through kernel
       (routing layer processes them, not module)
     - Module only needed for TUNNEL TERMINATION
     Conclusion: Module unload alone = NOT sufficient for blocking.
     Still need: iptables/nftables DROP rule for proto 47.
     Prevent module reload: echo "blacklist ip_gre" >> /etc/modprobe.d/blacklist.conf

Q95. Linux-ல் EtherIP receive handle பண்ற kernel code எங்கே உள்ளது?
A95. Kernel source analysis:
     EtherIP driver: net/ethernet/eth.c (partial)
     Protocol handler: net/ipv4/ip_input.c
     Proto 97 registration:
       drivers/net/ethernet/... (vendor specific)
     Check if proto 97 has handler:
       cat /proc/net/protocols | grep 97
     If no handler: packet dropped at kernel level.
     Raw socket can still receive:
       socket(AF_INET, SOCK_RAW, 97) = receives all proto 97
     Security implication: Raw socket root access needed,
     but if attacker has root = already compromised.

Q98. Automated daily report — encapsulation protocol attempts count பண்ண script?
A98. Bash script:
     #!/bin/bash
     # /usr/local/bin/encap-report.sh
     DATE=$(date +%Y-%m-%d)
     LOG="/var/log/syslog"
     REPORT="/var/reports/encap-$DATE.txt"

     echo "Encapsulation Attack Report — $DATE" > $REPORT
     echo "================================" >> $REPORT
     echo "" >> $REPORT

     for PROTO in "ETHERIP" "GRE-BLOCKED" "IPINIP-BLOCKED" "SixIN4-BLOCKED"; do
       COUNT=$(grep "$PROTO" $LOG | grep "$DATE" | wc -l)
       TOP_SRC=$(grep "$PROTO" $LOG | grep "$DATE" \
         | grep -oP 'SRC=\K[\d.]+' | sort | uniq -c \
         | sort -rn | head -3)
       echo "Protocol: $PROTO" >> $REPORT
       echo "  Total attempts: $COUNT" >> $REPORT
       echo "  Top sources:" >> $REPORT
       echo "$TOP_SRC" | sed 's/^/    /' >> $REPORT
     done

     mail -s "Encap Report $DATE" security@company.com < $REPORT
